# CLAUDE.md

Этот файл содержит указания для Claude Code (claude.ai/code) при работе с кодом в этом репозитории.

## Проект

**GeoPhotos** — приложение для Windows на Electron + Node.js для ручной привязки фото к карте (по образцу модуля Map в Lightroom). Git-репозиторий, удалённый — публичный на GitHub (релизы — GitHub Releases, сборка — GitHub Actions). Версия 0.37.0; каждая версия — одна фича или несколько связанных, очередная подверсия (`make-project.md`, п. 5), текущее состояние — в разделе «Статус» `make-project.md`.

## Команды

- `npm run dev` — запуск при разработке.
- `npm run build` — готовая программа: `dist/win-unpacked/GeoPhotos.exe`.
- `npm run typecheck` — проверка типов (main/preload/shared/tests и окно отдельно).
- `npm test` — unit-тесты; `npm run test:integration` — тесты с настоящим exiftool.
- Один тест: `npx vitest run tests/unit/<файл>.test.ts`.

Код: `src/main` (main-процесс), `src/preload` (мост, тип API в `api.d.ts`), `src/renderer` (окно), `src/shared` (общее, импорт как `@shared/...`). Подробности — `make-project.md`, п. 3.

## Документы

- `tz.md` — техзадание: итоговые требования, история версий и будущие фичи (п. 9), что не нужно делать. Главный источник требований; читать перед проектированием любой функции. При изменении требований обновлять этот файл.
- `tz-config.md` — обязательное ТЗ на устройство конфигурации программы.
- `make-project.md` — как создавать и развивать код: технические решения, структура, порядок работы над фичей и версиями, тесты, статус. Читать в начале каждой сессии и следовать ему; статус в нём обновлять по ходу работы.
- `CHANGELOG.md` — журнал изменений для пользователя; вести по `make-project.md`, п. 8.
- `tz_questions.md` — история вопросов и ответов, из которой собран `tz.md`. Использовать только для выяснения, почему принято решение. Если он расходится с `tz.md`, спросить пользователя.

## Правила работы с автором

- **ТЗ — только с согласия автора.** Перед любой правкой `tz.md` (требования, будущие фичи, планы) предложить точную формулировку и дождаться «да». Вопрос автора («как это работало бы?») — исследование, а не решение. Если неясно, «отложено» или «отказались», — спросить.
- **Предлагать фичи, но делать только согласованное.** Видишь разумную возможность, о которой автор не говорил, — коротко предложи с рекомендацией. Главный критерий автора — лаконичный интерфейс: программа должна быть профессиональной и законченной, без раздувания; фичи для редких случаев, добавляющие пункты меню, не предлагать. Ничего сверх оговорённого не менять самому.
- **Библиотеки.** Небольшую зависимость добавлять самому и сообщать о ней; радикальное (замена основной библиотеки, смена стека, заметный размер или лицензия) — согласовать (`make-project.md`, пп. 2, 6).
- **«Решение автора».** В `tz.md`, `make-project.md`, `CHANGELOG.md` решения записываются как «решение автора»; «пользователь» — тот, кто пользуется программой. Старые записи «решение пользователя» не переписывать.
- **Репозиторий публичный: без мест из данных автора.** В файлах репозитория (статус, журнал, ТЗ, README, тесты, сообщения коммитов) — никаких городов, стран и имён папок поездок из фото и треков автора. Тестовые данные описывать нейтрально («папка JPEG с телефона, 122 снимка»); марки и модели устройств можно. Перед коммитом проверять изменения на такие названия.
- **Сборка.** Если работа закончится сборкой (`npm run build`), в начале проверить, не запущен ли `dist\win-unpacked\GeoPhotos.exe` (он держит папку, сборка падает с EBUSY). Если запущен — сразу написать автору «Закрой GeoPhotos» и продолжать работу, собрать в конце. Закрывать программу автора самому нельзя.
- **Версия** поднимается только когда автор принял фичу (`make-project.md`, п. 5); «собери» — это только сборка программы для проверки.
