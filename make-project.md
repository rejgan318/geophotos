# Создание проекта GeoPhotos

Инструкция для Claude: как создавать и развивать код. Требования к программе — в `tz.md` и `tz-config.md`; этот файл описывает только процесс и технические решения.

Проект создаётся поэтапно, по шагам из `tz.md`, п. 9. Работа над шагом может занимать несколько сессий; текущее состояние всегда записано в разделе «Статус» в конце файла.

## 1. Начало каждой сессии

1. Прочитать этот файл целиком, затем `tz.md` и `tz-config.md`.
2. Посмотреть раздел «Статус»: какой шаг в работе, что сделано, что осталось.
3. Если в разделе «Открытые вопросы» есть пункты — напомнить о них пользователю.
4. Проверить фактическое состояние проекта: есть ли каркас (п. 4), совпадает ли он с решениями п. 2 и п. 3, проходят ли тесты. Если каркаса нет — создать его по п. 4. Если состояние расходится со «Статусом» — сказать пользователю и не продолжать, пока не решено, что верно.
5. Продолжить текущий шаг по п. 5.

## 2. Технические решения

Решения общие для всех шагов. Менять их — только по согласованию с пользователем (п. 6), с обновлением этого раздела.

| Что | Решение | Почему |
|---|---|---|
| Язык | TypeScript | Код переделывается между шагами; типы показывают, что сломалось. Связь main ↔ окно описывается типами в одном месте. |
| Сборка кода | electron-vite | Собирает main, preload и окна; подключает npm-пакеты в окне; TypeScript без отдельной настройки. В готовую программу не входит. |
| Готовая программа | electron-builder, папка с .exe (target `dir`, при необходимости zip) | Одна команда сборки. Portable-.exe не используется: распаковывается при каждом запуске. При разработке — `npm run dev`. |
| Интерфейс | Без фреймворка: TypeScript + DOM. React не используется. | Почти всё окно — карта, которой управляет Leaflet. Перетаскивание на карту и маркеров проще без обёрток. Встроенных редакторов настроек нет (`tz-config.md`, п. 6). |
| Меню | Системное меню Electron (`Menu`) | ТЗ, п. 4.9. |
| Карта | Leaflet + Leaflet.markercluster | Тайлы по шаблону адреса из конфига, подпись правообладателей, группировка с числом, перетаскивание маркеров. |
| exiftool | Свой модуль в main: один процесс exiftool в режиме `-stay_open`, ответы в JSON. Путь — из настроек. | Без перезапуска exiftool на каждый файл — быстро на сотнях фото. Пакет `exiftool-vendored` не используется: он ставит свой exiftool, а по ТЗ (п. 2.2) нужен внешний. |
| TIFF → JPEG, уменьшение превью | `sharp` | Быстро, работает в main. |
| HEIC → JPEG | Встроенное JPEG-превью через exiftool; если его нет — `heic-decode` в main | `sharp` в стандартной сборке HEIC не читает. HEIC с телефона содержит превью 1080×1440 — достаточно для миниатюр и быстро. Полное декодирование (`heic-decode`) — только для HEIC без превью; если станет частым или понадобится крупный показ — вынести в фоновый поток. |
| Конфиг | `jsonc-parser`, `ajv` | `tz-config.md`, пп. 4–5. |
| Локализация | JSON-файл на язык, своя функция перевода | Библиотека не нужна (ТЗ, п. 2.3). |
| Лог | `electron-log` с ротацией нескольких файлов | ТЗ, п. 6.9; хранение нескольких старых файлов требует своей настройки ротации. |
| Тесты | `vitest` | п. 7. |

Окружение (проверено 2026-11-10): Node.js 26.13 (LTS), npm 11.20, exiftool 13.62 (в PATH), git 2.55, GitHub CLI 2.103. Версии пакетов npm фиксируются точно в `package.json` (без `^`), Electron — актуальная стабильная на момент создания каркаса.

Проверено на шаге 1: `sharp` работает в собранной программе (распакован из asar через `asarUnpack`); миниатюры RAW, DNG и HEIC — из встроенного превью.

## 3. Структура проекта

```
src/
  main/        процесс main: окно, меню, exiftool, файлы, конфиг, лог
  preload/     мост между main и окном (contextBridge)
  renderer/    окно: карта, лента, строка состояния
  shared/      общее для main и окна: типы, описание IPC, чистая логика без Electron
config/        настройки по умолчанию (tz-config.md, п. 3.1)
schemas/       JSON Schema конфигов (tz-config.md, п. 2)
locales/       файлы локализации: en.json, ru.json
tests/
  unit/        тесты логики
  integration/ тесты с настоящим exiftool (helpers.ts — общие функции)
scripts/       служебные скрипты
```

Устройство кода (шаг 1):
- `src/main/index.ts` — запуск: настройки → язык → лог → проверка exiftool → окно; меню, открытие папки, протокол `thumb://` для миниатюр.
- `src/main/settings.ts` — чтение и проверка конфигов, создание пользовательского файла; `src/shared/settings.ts` — типы и наложение по полям.
- `src/main/exiftool.ts` — процесс exiftool (`-stay_open`); `src/main/folder.ts` — чтение папки; `src/main/thumbnails.ts` — миниатюры.
- `src/shared/metadata.ts` — разбор ответа exiftool: координаты, даты, ошибки, порядок ленты; `src/shared/formats.ts` — форматы.
- `src/shared/ipc.ts` — каналы IPC и их данные; `src/preload/` — мост; `src/renderer/src/` — карта (`map.ts`), лента (`strip.ts`), запуск окна (`main.ts`).
- Миниатюры делаются в main по запросу окна (`<img src="thumb://f<поколение>/<id>">`, ленивая загрузка), не больше 3 одновременно, кешируются в памяти до открытия другой папки.

- Логика, которую можно проверить без Electron и без файлов (разбор координат, сортировка, наложение конфигов, тип формата), — в `src/shared` или в отдельных модулях без зависимостей от Electron, чтобы её покрывали unit-тесты.
- Окно не имеет доступа к Node.js (`contextIsolation: true`, `nodeIntegration: false`). Всё обращение к файлам и exiftool — в main через IPC. Каналы IPC и их типы описаны в одном файле в `src/shared`.
- `config/`, `schemas/`, `locales/` входят в сборку вне asar (`extraResources`): пользовательский конфиг ссылается на схему через `"$schema"`, а внешний редактор (VS Code) должен открыть её по обычному пути. Путь к схеме в создаваемом конфиге (`tz-config.md`, п. 6.3) — абсолютный путь к схеме в установленной программе (в режиме разработки — в проекте).
- Порядок по `tz-config.md`, п. 2.1: сначала схема, затем конфиг по умолчанию, затем код.

## 4. Каркас (до шага 1)

Выполняется, только если каркаса нет (п. 1.4). Каркас — пустое, но запускающееся приложение.

1. `git init`, `.gitignore` (node_modules, out, dist, логи, `.env`).
2. Приватный репозиторий на GitHub через `gh repo create geophotos --private --source . --remote origin`. Если `gh` не авторизован — попросить пользователя выполнить `gh auth login`.
3. `package.json`, electron-vite с TypeScript, electron-builder, vitest. Структура папок по п. 3.
4. Скрипты npm: `dev` (запуск при разработке), `build` (готовая программа), `typecheck`, `test`, `test:integration`.
5. Проверить: `npm run dev` открывает пустое окно; `npm run build` даёт работающий .exe; `npm run typecheck` и `npm test` проходят.
6. Обновить `CLAUDE.md`: проект — git-репозиторий, есть код, команды запуска и тестов.
7. Первый коммит и push — с подтверждения пользователя.
8. Отметить каркас в «Статусе».

## 5. Выполнение шага

1. Взять состав и критерии готовности шага из `tz.md`, п. 9. Делать только то, что входит в шаг; но так, чтобы следующие шаги не потребовали ломать архитектуру (`tz.md`, п. 9).
2. Если в ТЗ что-то неясно или противоречит — спросить пользователя, а не додумывать. Решение записать в `tz.md`.
3. Писать код и тесты вместе (п. 7). По мере работы обновлять «Статус» (что сделано, что осталось) и журнал изменений (п. 8).
4. Перед передачей пользователю: `npm run typecheck`, `npm test`, `npm run test:integration` проходят; программа запускается через `npm run dev`; собственная проверка тех критериев готовности, которые можно проверить без пользователя.
5. Передать шаг пользователю: что сделано, как проверить, что не проверено.
6. Шаг готов только после подтверждения пользователя, что всё работает как ожидалось. Найденные пользователем ошибки — исправить (п. 7) и передать снова.
7. После подтверждения: отметить шаг готовым в «Статусе» с датой, закрыть раздел «В работе» в журнале (п. 8); коммит и push — с подтверждения пользователя.

**Окружение Claude.** Команды Claude выполняются в изолированной среде: файлы в `%APPDATA%\GeoPhotos`, которые меняли запуски Claude (лог, `state.json`, `settings.json`), Claude видит как свою отдельную копию — записи сеансов пользователя там не видны. Чтобы посмотреть лог или состояние сеанса пользователя, попросить пользователя оставить программу открытой и прочитать файлы через неё: `node -e "process._debugProcess(<pid>)"` открывает отладчик Node в main-процессе на 127.0.0.1:9229 (после проверки закрыть: `require('inspector').close()`), либо попросить пользователя прислать файл.

## 6. Переделка сделанного

Переделывать код прошлых шагов можно и нужно, если этого требует текущий шаг.

- Перед переделкой сказать пользователю, что и зачем меняется.
- Крупные переделки — замена библиотеки, изменение структуры, изменение решений п. 2 или п. 3 — сначала согласовать с пользователем.
- После переделки — все тесты и повторная проверка критериев готовности прошлых шагов.
- Если меняются решения — обновить п. 2 или п. 3 этого файла.

## 7. Тесты

- **Unit-тесты (`tests/unit`, обязательно).** Чистая логика: разбор координат (`tz.md`, п. 4.12 — все примеры из ТЗ и записи, которые должны отклоняться), порядок источников координат (п. 3.7), сортировка ленты (п. 4.2), тип формата и способ записи (п. 3.3), имя XMP (п. 6.4), наложение и проверка конфигов (пп. 8.3–8.4), одинаковый набор ключей во всех файлах локализации.
- **Интеграционные тесты (`tests/integration`, обязательно).** Настоящий exiftool на копиях файлов во временной папке: чтение координат, запись и обратное чтение, запись RAW только в XMP с сохранением прежнего содержимого XMP, отсутствие `*_original`, ошибка на файле только для чтения при успешной записи остальных.
- **Тестовые файлы.** Простые случаи (битый файл, координаты только во встроенном XMP, разные координаты в XMP рядом и в EXIF, южное и западное полушарие, пара RAW+JPEG с общим XMP, фото без даты) интеграционные тесты создают сами во временной папке (sharp + exiftool) и удаляют после себя. Настоящие снимки (HEIC с телефона, CR2 с XMP и без, DNG и другие) — личные фото пользователя, в git не кладутся. Они лежат вне проекта, в `D:\dev\data\geophotos-testdata`:
  - `master\` — эталон. Программа и тесты его не изменяют. Интеграционные тесты копируют файлы из него во временную папку и работают с копией.
  - `work\` — копия для ручной проверки пользователем; может портиться, восстанавливается копированием из `master\`.

  Путь к `master\` тесты берут из переменной окружения `GEOPHOTOS_TEST_DIR`, а если она не задана — `../data/geophotos-testdata/master` относительно проекта. Если папки нет или она пуста, тесты с настоящими снимками пропускаются с сообщением.
- **Интерфейс** проверяет пользователь вручную по критериям готовности шага.
- На каждую найденную ошибку сначала пишется тест, который её воспроизводит, затем исправление.

## 8. Журнал изменений

`CHANGELOG.md` в корне проекта — история разработки для пользователя.

- Пишется по-русски, о том, что изменилось для пользователя: добавлено, исправлено, изменено, принятые решения. Без подробностей кода — они в истории git.
- Сверху — раздел «В работе». Запись добавляется сразу при изменении, видном пользователю (новая возможность, исправленное замечание, решение по ТЗ), а не в конце шага.
- Внутри раздела — подзаголовки по шагам и группы «Добавлено», «Исправлено», «Изменено», «Решения». Исправление замечания пользователя — одной строкой: что было не так и как теперь.
- Когда пользователь принимает шаг: раздел «В работе» получает заголовок «Шаг N — название — дата», над ним открывается новый пустой «В работе»; в том же коммите — отметка в «Статусе».
